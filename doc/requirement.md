# AI 小说问答助手需求文档

## 1. 项目背景

本项目是一个简单的 AI 小说问答助手。用户提供一组小说原文后，可以在控制台输入问题，系统根据小说原文检索相关内容，并让大语言模型基于检索到的原文片段进行回答。

项目当前处于多书 RAG MVP 阶段，目标不是一次性做成完整产品，而是先验证最核心链路：小说导入、EPUB 清洗、文本切片、向量化、多书召回、rerank 排序、基于原文回答。

## 2. 核心目标

项目的核心目标是实现一个“基于小说原文的问答助手”：

- 用户可以围绕小说人物、情节、事件、关系等内容提问。
- 系统回答必须来自小说原文提供的证据。
- 当小说原文中没有足够依据时，系统应明确说明无法从原文确认，而不是让 LLM 自由猜测。
- 用户可以查看系统召回的原文片段，便于判断回答是否可靠。

## 3. 核心特色

本项目最重要的特色是：所有回答必须基于小说原文。

普通 LLM 容易根据通用知识或语言模式生成看似合理但未必真实的答案。对于小说问答场景，这会带来明显问题：

- 编造不存在的情节。
- 混淆人物关系。
- 将其他作品或常见套路套用到当前小说。
- 对原文没有明确描述的内容进行过度推断。

因此，本项目采用 RAG 技术，将小说原文作为唯一可信知识来源。LLM 只负责根据召回的原文片段组织语言，不负责凭空补充事实。

## 4. 用户场景

### 4.1 查询剧情细节

用户想知道某个事件是否发生过、如何发生、相关人物是谁。系统应召回相关原文并给出简明回答。

示例问题：

- 主角第一次遇到某个人是在什么时候？
- 某个事件的起因是什么？
- 某个地点发生过哪些重要情节？

### 4.2 查询人物关系

用户想确认人物之间的关系、冲突、身份或态度变化。系统应基于小说中明确出现的描述进行回答。

示例问题：

- A 和 B 是什么关系？
- A 为什么不信任 B？
- 某个人的真实身份有没有被揭示？

### 4.3 查看原文依据

用户不只需要答案，还需要知道答案来自哪些原文片段。MVP 阶段应支持展示召回片段，方便人工检查 RAG 效果。

### 4.4 调试召回效果

开发者需要在不调用 LLM 的情况下，只查看问题对应的召回结果，用来判断切片、向量化和相似度检索是否有效。

## 5. MVP 范围

MVP 阶段只实现最小可用能力：

- 支持导入多本本地小说文本。
- 支持将 EPUB 清洗为纯文本后进入索引。
- 支持按章节、场景和自然段进行结构感知切片。
- 支持调用外部 embedding API 生成向量。
- 支持将切片、chapter/scene metadata 和向量保存到本地文件。
- 支持控制台输入问题。
- 支持根据用户问题进行 embedding dense + BM25 sparse 两路召回，并利用 book/scene metadata 补充连续上下文。
- 支持多书合并索引，所有跨 chunk/scene 扩展都使用 `(book_name, chunk_index)` 和 `(book_name, scene_id)` 避免跨书串台。
- 支持书籍路由，默认从候选中选择 5 本相关书参与书内 scene 聚合。
- 支持 qwen3-rerank 对候选池重排，默认对 30 个候选 chunk 打分。
- 支持在不破坏高置信 Top4 的前提下，用第 5 位 rescue slot 补充强 BM25 证据片段。
- 支持将召回片段拼接给 LLM 生成回答。
- 支持展示回答引用的原文片段。
- 支持仅查看召回结果，不调用 LLM。
- 支持最小 Flask API 和轻量 Web 聊天前端，便于本地演示和查看召回片段。

## 6. 非目标范围

以下能力不进入 MVP 阶段：

- 完整 Web 产品或桌面客户端。
- 多用户系统。
- 完整多小说书库管理界面。
- 登录、权限、收藏、历史记录等产品功能。
- 复杂目录解析、跨卷书库结构化管理。
- 正式向量数据库。
- 知识图谱。
- 完整线上评测平台。
- 多模型路由。
- 长期记忆或用户画像。
- 在线爬取小说。

这些能力可以在后续版本中逐步扩展。

## 7. 基本流程

### 7.1 建索引流程

1. 开发者准备多本纯文本小说，或先将 EPUB 清洗为纯文本。
2. 系统读取每本小说文本，并为每本书指定 `book_name`。
3. 系统按章节、场景、自然段和句子兜底策略切分文本。
4. 系统只对 chunk 正文调用 embedding API 生成向量。
5. 系统将 chunk 文本、chapter/scene metadata 和向量保存到本地索引文件。

### 7.2 问答流程

1. 用户在控制台输入问题。
2. 系统调用 embedding API 将问题转换为向量。
3. 系统在本地索引中计算问题向量和所有 chunk 向量的相似度。
4. 系统同时对原始问题文本执行 BM25 sparse 召回。
5. 系统按向量分 0.8、BM25 分 0.2 做归一化融合。
6. 系统根据融合候选选择相关书籍，当前默认 `book_route_count=5`。
7. 系统在候选书内部按 scene 聚合，对命中 chunk 做前 2 后 1 的相邻扩展，并补充同场景上下文。
8. 在线问答和 eval rerank 模式下，系统使用更宽的 dense/BM25 候选视野，默认 `vector_top_n=100`、`bm25_top_n=100`，并对最终 30 个候选 chunk 调用 qwen3-rerank。
9. 系统保留最终 top_k 片段，且默认单本书最多占 3 个位置。
10. LLM 根据上下文生成回答。
11. 系统输出答案和引用片段。

### 7.3 召回查看流程

1. 用户在控制台输入问题。
2. 系统执行 embedding dense + BM25 sparse 两路召回、多书路由、scene-expanded 后处理和 rescue slot。
3. 系统输出 top_k 召回片段和相似度分数。
4. 系统不调用 LLM。

## 8. 回答原则

系统回答必须遵守以下原则：

- 只基于召回到的小说原文片段回答。
- 不使用 LLM 的通用知识补全小说事实。
- 不编造人物、地点、事件或关系。
- 如果上下文不足，应明确说明“原文中没有足够信息确认”。
- 如果答案来自多个片段，应尽量合并信息，并保留引用来源。
- 回答应简洁清楚，避免无依据的长篇推测。

## 9. 成功标准

MVP 被认为可用，需要满足以下标准：

- 能成功读取多本小说纯文本文件。
- 能将 EPUB 清洗为纯文本后用于建索引。
- 能按章节 > 场景 > 自然段的层级切分文本，超长自然段按句子兜底。
- 能保存 `chapter_title`、`chapter_index`、`scene_index`、`scene_id` 等 metadata。
- embedding 只使用 chunk 正文，不拼接 metadata。
- 能为每个 chunk 生成向量并保存本地索引。
- 用户输入小说相关问题时，系统能在多书合并索引中召回相关原文片段，并尽量补齐同场景连续上下文。
- 多书 RAG 需要避免不同书之间相同 `scene_id` 或 `chunk_index` 导致的扩展串台。
- 十本书 rerank 评测目标 Recall@5 接近或超过 89%。
- 当前十本书最佳评测目录为 `rag_eval_ten_book_qwen3_rerank_route5_v100_b100_top30_20260430_1645`，Recall@5 89.34%，MRR 0.8276，Missed Count 21，Candidate Hit@30 91.37%。
- 系统能基于召回片段生成回答。
- 回答中能看到对应的引用片段。
- 本地 Flask API 和轻量前端能提交问题、展示回答、展示引用片段和当前书库统计。
- 对于原文中没有依据的问题，系统不会编造答案。
- 开发者可以单独查看召回结果，调试 RAG 效果。
- 局部剧情类问题优先关注 Top5 上下文覆盖率；引入 rerank 后，Recall@1 和 MRR 也作为排序质量的重要指标。

## 10. 后续优化方向

MVP 验证通过后，可以考虑以下优化：

- 扩展到更多卷小说。
- 引入向量数据库。
- 增强章节识别和章节级引用。
- 优化 chunk 切分参数和 scene 边界策略。
- 继续优化 hybrid retrieval，避免上下文过度集中于少数场景。
- 增加 scene 聚合分数策略，综合多个候选 chunk 的相关性。
- 继续优化候选池召回，优先降低 Candidate Miss@30。
- 评估高召回模式，例如 `rerank_candidate_top_n=50` 的成本收益。
- 完善 Web 前端。
- 增加问答历史。
- 增加回答质量评测。
- 增加不同模型配置。
- 支持更多文档格式，例如 EPUB、PDF、DOCX。
